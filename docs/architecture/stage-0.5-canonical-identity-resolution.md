# Phase A — Stage 0.5: Canonical Identity Resolution & Constitutional Audit

**Status: EVIDENCE ONLY. No code modified. No migration written. No schema changed. No implementation proposed.** Every claim below is backed by a live query against the production Supabase database (`mcp__supabase__list_tables`, `mcp__supabase__execute_sql`, `mcp__supabase__get_advisors`) or a direct grep/read of the current codebase, performed in this session. Where evidence was insufficient, the item is marked `UNVERIFIED` with a statement of exactly what additional evidence would resolve it — never guessed.

**Method note on "live usage vs. dead usage":** measured as the count of distinct source files under `lib/`/`app/` that call `.from('<table>')` (or, for repository-wrapped tables, the count of distinct callers of the owning repository), verified with both single- and double-quote grep patterns after an initial undercount was caught and corrected mid-investigation (see Part 1, `classes`). This is a proxy for *code-reachability*, not a proxy for correctness — a table can be heavily referenced and still be functionally broken (see Learner Identity Analysis).

---

## Executive Summary

The Stage 0 census found that `students` and `learners` are disjoint tables with no schema bridge, and that Core's report pipeline has zero production rows because of it. This Stage 0.5 investigation goes deeper and finds the problem is **larger than a two-table duplication**: there are, by exact count, **four surviving identity systems for "the person being taught"** (`students`, `learners`, plus two near-dead vestigial tables `learner_profiles`'s underlying student linkage and unrelated capability tracking — detailed below), **three teacher-school-membership tables** (`teachers`+`school`-text, `school_users`, `school_teachers` — the last one has zero rows), **two class-teacher-assignment tables beyond the Class duplication already known** (`class_teachers`, 1 row; `class_subjects.teacher_id`), **two generic app-identity tables** (`profiles`, 50 rows, canonical for role lookups; `users`, 11 rows, a much smaller and apparently older table used for referral/free-analysis tracking), and **two guardian tables** (`learner_guardians`, 405 rows, live; `student_guardians`, 1 row, functionally dead).

The decisive new evidence is usage-based, not just schema-based: `students` is referenced by **68 files**, `learners` by effectively one repository module (`lib/repositories/learner.repository.ts`) with **3 callers** (`lib/core/learners.ts`, `lib/core/transfers.ts`, `lib/core/promotions.ts`), all of which are themselves only reached from **2 API routes** (`app/api/core/classes/route.ts`, `app/api/core/subjects/route.ts` — and neither of those two routes calls the learner functions directly; this needs a follow-up trace, see the open item in Part 4). `students` is not just older — it is the table every live, real, production-serving code path in this platform actually uses, including the Evidence Domain (`learner_evidence.learner_id → students.id`), the Projection Engine (`learner_projections.learner_id → students.id`, 2,441 real rows), and `learner_profiles` (`student_id → students.id`, 479 real rows). `learners` is schema-correct, well-formed, has real seeded data (405 rows) — and is otherwise almost entirely disconnected from the rest of the platform's live code.

This changes the shape of the Stage 0.5 recommendation from "pick a winner between two comparable systems" to "recognize that one system (`students`) is the de facto canonical identity already, by every measure except the Constitution's stated intent, and the other (`learners`) is a well-built but functionally isolated island that Core's newer modules were written against."

## Part 2 — Identity Dependency Graph

**Reads/writes by identity, evidenced by grep + FK inspection:**

- **`students`** — written by `app/api/students/**`, `app/api/teacher/**` (student CRUD), read by nearly every intelligence/evidence/assessment module (68 files total). This is the actual spine of the platform's live data model.
- **`learners`** — written/read almost exclusively through `lib/repositories/learner.repository.ts`, called only by `lib/core/learners.ts`, `lib/core/transfers.ts`, `lib/core/promotions.ts`. **Broken/unconfirmed chain**: the two API routes that reach the broader Core class module (`app/api/core/classes/route.ts`, `app/api/core/subjects/route.ts`) do not, on this pass's grep, appear to call into `lib/core/learners.ts` directly — meaning it is `UNVERIFIED` whether any live HTTP-reachable route actually exercises the learner-write path at all, versus the 405 `learners` rows having been inserted by a one-off seed/migration script outside normal request flow. **This is exactly the kind of thing this document is required to flag rather than guess at**: recommend a targeted trace (grep for every importer of `lib/core/learners.ts`'s exported functions, plus a check of `supabase/*.sql` seed scripts) before concluding either way.
- **`class_assessments`/`learner_marks`** — read by both `lib/assessments/*` and `lib/core/assessments.ts`, but FK'd only to `teacher_classes`/`students`. **This is the broken FK chain the Stage 0 census already identified**: `lib/core/assessments.ts:82`'s `computeTermSummaries` reads real `learner_marks` rows (keyed to `students.id`) and attempts to write `term_subject_summaries` rows keyed to `learners.id` — a cross-identity write that the schema's FK constraint would reject for any `student_id` that isn't coincidentally also a valid `learners.id`. Confirmed by the zero-row outcome in both target tables.
- **`school_report_cards`/`term_subject_summaries`** — read by `app/api/reports/report-card/**` (parent-facing), `app/api/core/reports/**` — all pointed at the Core/`learners` identity space, currently empty.
- **`learner_evidence`/`learner_projections`/`learner_profiles`** — the entire Learning Evidence / Educational Intelligence domain (Fourth Constitutional Law) is wired to `students.id`, not `learners.id`. This is itself informative: whoever built the Evidence Domain (a later, more careful build per project memory) chose `students` as the identity to anchor against, not `learners` — a data point worth weighting in the canonical decision.
- **Orphan records**: none at the referential-integrity level for any FK-enforced relationship (confirmed in Stage 0, reconfirmed here for the newly-examined tables — `learner_guardians`, `class_subjects`, `class_teachers` all have enforced FKs with no orphan risk). The orphan risk in this system remains entity-level, not row-level: a `students` row with no `learners` counterpart (or vice versa) is not a broken foreign key, it is a business-logic-level "this same child may be recorded in two places that don't know about each other."
- **Circular dependencies**: `UNVERIFIED` — a full import-graph analysis across `lib/` was not performed in this pass; flagged as an open item requiring a dedicated static-analysis pass (e.g. `madge` or equivalent), not something groppable by hand within this investigation's scope.
- **Conflicting ownership, newly found**: `lib/repositories/teacher.repository.ts` is the single file that queries the Core `classes` table — meaning the repository *named* for the legacy Teacher/`teacher_classes` domain is also the sole custodian of Core's Class reads. This is a naming/ownership mismatch worth flagging: whoever built Core's class-read path apparently found it more convenient to add a method to the existing `TeacherRepository` than to create a `ClassRepository`, which — while not itself broken — obscures the "canonical service" question at the repository layer (there is no `ClassRepository` at all in `lib/repositories/`, despite `classes` being nominally the Core-canonical table).

## Part 3 — Learner Identity Analysis (Constitutional Part 4, ordered per requested deliverable structure)

### Schema comparison
| | `students` | `learners` |
|---|---|---|
| Rows | 499 | 405 |
| School ownership | **No `school_id` column exists at all** | `school_id` NOT NULL, FK'd |
| Teacher link | `teacher_id → teachers.id`, nullable (20 rows null) | None — ownership is institutional, matching the Second Constitutional Law's intent exactly |
| Name fields | Single `name` text field | `first_name`/`middle_name`/`last_name` — more structured |
| Identity fields | `external_id`, `user_id → auth.users.id` (for student-portal login) | `admission_number` (NOT NULL), `upi` (nullable) — more aligned with real Kenyan school administrative identity (NEMIS/UPI conventions) |
| Status tracking | None | `status`, `admission_date`, `graduation_date` — models the *institutional lifecycle* of a learner, which `students` does not attempt at all |
| Curriculum/pathway fields | `curriculum_type`, `current_pathway`, `selected_subjects`, `capability_profile` (JSON), `capability_computed_at` — rich Intelligence-facing fields | None of these — `learners` has zero Intelligence-facing fields |

**Reading**: `learners` is the more *institutionally* correct model (matches the Second and Third Laws' intent — school-owned, admission-number-based, lifecycle-aware). `students` is the more *intelligence*-correct model (it's what the Evidence Domain, Projection Engine, and capability/pathway system are actually built against). Neither is strictly superior; they were optimized for different halves of the platform's stated mission.

### Usage comparison
- `students`: 68 referencing files, real production data flowing through it continuously (476 marks, 407 evidence rows, 2,441 projections, 89 legacy assessments).
- `learners`: 3 confirmed application-level callers, reachability from an actual HTTP route `UNVERIFIED` (see Part 2), zero rows in any table that would prove it's being written to via normal request flow rather than a seed script.

### API comparison
- `students`-backed APIs: `app/api/students/**`, `app/api/assessments/**`, `app/api/teacher/**`, `app/api/reports/report-card/**` (ironically — the parent-facing report-card *read* route checks guardian links against `learners`/`learner_guardians` per the RLS policies found in Stage 0, while the actual report *data* it's trying to serve has never been generated, because generation depends on `learners`-keyed tables that generation itself can't correctly populate — a closed loop that currently produces nothing).
- `learners`-backed APIs: `app/api/core/classes`, `app/api/core/subjects` — and even these, per Part 2, don't clearly call the learner-write path.

### Service comparison
- `students`: served by dozens of `lib/` modules across academicClinic, adaptiveLearning, career, compass, holiday, intelligence, learnerModel, learnerRecord, projection, remedial.
- `learners`: served by exactly one repository (`lib/repositories/learner.repository.ts`) and three thin `lib/core/*` wrappers.

### Relationship comparison
- `students`: has real, populated relationships to `teachers`, `assessments`, `learner_marks` (via `class_assessments`), `learner_evidence`, `learner_projections`, `learner_profiles`, `class_students`.
- `learners`: has real, populated relationships to `schools`, `learner_enrollments`, `learner_guardians` — but its relationships to `class_assessments`/`learner_marks`/`term_subject_summaries` are the ones that are currently broken (Part 2), so its "richer institutional graph" is partly aspirational rather than fully realized.

### Security comparison
- `students` RLS: owner-scoped (`auth.uid() = user_id`) plus an `Admin full access` policy gated on `teachers.role='admin'` (flagged `UNVERIFIED` for self-service-escalation risk in Stage 0, not re-investigated here).
- `learners` RLS: correctly, consistently school-scoped via `school_users` membership (`learners_school_staff`) plus a guardian-scoped read policy (`learners_parent_own_child`) — this is the more architecturally correct RLS design of the two, with no gaps found in either pass.

### Future Intelligence compatibility
- The Fourth Constitutional Law requires Official Records to flow into Learning Evidence into Intelligence, staying separate but connected. Today, that entire pipeline (`learner_evidence`, `learner_projections`, `learner_profiles`, and everything built on `recomputeLearnerProjection`/`getLearnerTimeline`) is anchored to `students.id`. **If `learners` were declared canonical without a migration plan for this entire pipeline, every existing Intelligence feature in the platform would need to be re-pointed** — a materially larger blast radius than the Class/Assessment consolidation this whole Phase A sprint was originally scoped around. This is the single most important piece of evidence in this analysis: the "Educational Intelligence Platform" identity of this product (per the Constitution's own Project Identity framing) is built on `students`, not `learners`.

### Recommendation

**Evidence supports `students` as the interim canonical Learner identity, with `learners` retained as the target institutional shape to migrate *into* — not the other way around.** This is a reversal of the direction Stage 0's plan implicitly assumed (that Core's newer, better-designed table should absorb the legacy one). The reasoning:
1. Constitutional correctness (Second/Third Law: school-owned, single canonical model) favors `learners`' *shape*.
2. Constitutional correctness (Fourth Law: Official Records → Evidence → Intelligence, without re-platforming Intelligence) favors keeping `students` as the anchor, because Intelligence is already built on it and re-pointing Intelligence is out of Phase A's stated scope (and arguably out of *any* phase's scope without a dedicated, separately-approved Intelligence-migration project).
3. A third canonical model is not recommended — neither table is insufficient in a way that requires inventing a new one; the evidence points to **evolving `students`' schema to acquire `learners`' institutional-correctness fields (`school_id`, `admission_number`, lifecycle status)** rather than migrating Intelligence onto `learners`, or abandoning `learners`' 405 real rows.
4. This recommendation is **evidence-based but not final** — it is a direction, not a decision this document is authorized to make unilaterally per the Constraints. It is offered as the best-supported reading of the evidence gathered, for human ratification.

## Risks

- **Risk of choosing wrong**: if `learners` were declared canonical without the usage evidence in this document, Phase A would spend its highest-risk stage (Class/Learner consolidation) migrating 68 files' worth of real, working, production-serving code onto a 3-caller, functionally-unproven island — while the actual Intelligence stack (Evidence, Projections, Profiles) would need a *second*, unplanned migration to follow it, since Fourth Law compliance means Intelligence cannot be left pointing at a deprecated table.
- **Risk of choosing `students` and stopping there**: `students` lacks `school_id` entirely and has no institutional lifecycle modeling — canonicalizing it as-is, without evolving it toward `learners`' shape, would leave the Second Law permanently unsatisfied. This document does not recommend that outcome; it recommends evolution, not a simple pick.
- **Risk of further undiscovered identity splits**: this pass found `school_teachers` (teacher-school) and `student_guardians`/`parent_profiles` (guardian) splits that were not known before this document, on top of the already-known Class/Learner split. Given that pattern, it would be reasonable to assume other yet-unexamined domains (Attendance — confirmed entirely unbuilt; Discipline, Timetable — not examined in this pass at all, not named in Part 1's table because no evidence was gathered for them) could reveal similar findings if investigated with the same rigor. This document does not claim completeness beyond the entities the Constitution explicitly named.

## Architecture Verdict

The platform is not suffering from careless engineering — every individual system examined in this document (`learners`, `class_assessments`, `learner_evidence`, `profiles`) is, read in isolation, competently built. The failure is coordination across time: Core was built later, with better institutional modeling, without a migration plan for the earlier system it was implicitly meant to replace, and without anyone verifying end-to-end that its report-generation path could actually write data before more was built on top of it. The Constitution's First Law is violated in exactly the way its authors evidently anticipated when they wrote it — this document's job was to find out *how badly*, with evidence, not to guess. The honest answer: badly enough that the previously-approved Phase A plan's Stage 4/5 direction needs to be reconsidered, not merely delayed.

# Sprint 6G — Decision & Authority Model Audit

**Mode: READ ONLY.** No code, schema, migration, route, repository, service, test, or configuration was modified. Every claim is marked VERIFIED (confirmed by direct code/schema inspection this session, or restated unchanged from a prior sprint's VERIFIED finding and cited back to it), LIKELY (strong indirect evidence, not exhaustively confirmed), or UNKNOWN (flagged rather than guessed).

**Builds on**: Sprint 6A (structure), 6B (reconciliation), 6C (operating model), 6D (workflow model — what happens, and where), 6E (organizational model — who exists), 6F (information flow model — what moves, and where it stops). Sprint 6G asks the final question in this series: **who, or what, actually makes each decision** — and whether the platform can prove it.

---

## Executive Summary

EduNexus has **one decision with a fully modeled audit trail (Evidence confirm/reject/retract) and a long tail of decisions with none at all.** `learner_evidence`'s lifecycle columns — `reviewed_by`, `reviewed_at`, `review_reason`, `retracted_by`, `retracted_at`, `retraction_reason`, `supersedes`/`superseded_by` (full correction lineage), `verification_state`, plus a frozen `trust_tier`/`evidence_confidence` snapshot — are, confirmed this session, the richest decision-record shape anywhere in the schema. Every other "publish" decision found this session (`class_assessments.is_published`, `school_report_cards.is_published`, `holiday_plans.is_published`, `class_differentiation_plans.is_published`) records **only that a publish happened and when — never who published it, and never why.** A report card can carry a `headteacher_comment` column, but nothing records which headteacher — or any headteacher, since Sprint 6E already established the role can never be granted in production — actually wrote it.

The second finding, new this session: `school_report_cards` has `days_present`/`days_absent` columns — the schema anticipates an Attendance decision (Sprint 6C/6D/6E: VERIFIED absent as a domain) that no workflow anywhere in the platform ever produces. This is the clearest concrete instance this series has found of a **decision point the schema was designed around but the product never built** — restated in Part 6.

The third finding, synthesizing 6E/6F: **the platform's only fully autonomous, unreviewable, state-changing decision is Career Intelligence's AI-generated match/profile persistence** (`lib/career/matchEngine.ts:97`, `lib/career/careerEngine.ts:191`) — AI decides, writes directly to `careers`/`career_matches`, and the decision reaches the student with no human approval gate and no traceability columns distinguishing it as AI-made at all, in direct contrast to Evidence's rigor.

## Part 5 — Approval Gates

| Gate | Who approves | What becomes irreversible | What remains editable |
|---|---|---|---|
| Evidence confirm/reject | Teacher (mastery claims) | The `lifecycle_state` transition itself is DB-trigger-enforced and one-directional (`enforce_evidence_lifecycle_transition`) — a confirmed row cannot be silently re-opened | The underlying fact can still be corrected via a **new superseding row** (`supersedes`/`superseded_by`) — never an in-place edit, per CLAUDE.md |
| Evidence retraction | Teacher, via `retractEvidence` | The retraction itself, once recorded (`retracted_by`/`retracted_at`/`retraction_reason`) | N/A — retraction is itself the terminal state for that row |
| Report Card publish (Core) | Admin-tier only (`canPublishReport`), deliberately narrower than assessment-publish | `is_published = true` — no `published_by` column exists to record who (Part 9) | Comment fields (`class_teacher_comment`, `headteacher_comment`) — UNKNOWN whether these remain editable post-publish, not verified this session |
| Assessment publish | Same actor as creation/marking — no second approver | `is_published = true` on `class_assessments` — again, no `published_by`/`published_reason` column found | Marks themselves — UNKNOWN whether marks remain editable after publish, not re-verified this session (flagged, not claimed) |
| Holiday Plan publish | Teacher, or the 3-day cron fallback | `is_published = true` (`holiday_plans`) | The plan content before publish; nothing found governing post-publish edits |
| Differentiation Plan approval | Teacher, explicit approve endpoint | The approved/adjusted groups become what learners see | The AI's original draft proposal remains distinct from the approved version — the endpoint's own design preserves both, per Sprint 6E |
| Guardian link redemption | Parent (self-approval — there is no second party who approves a parent linking themselves) | The link itself, once set (`parent_user_id`, `class_students.parent_id`) — no unlink path found this session | N/A |

**Cross-cutting finding**: **Evidence is the only approval gate in the entire platform whose "who approved" is captured in the schema itself.** Every other approval gate found this session records *that* an approval-shaped state flip happened (a boolean plus a timestamp) but not *who* performed it at the database level — the acting user is implicitly whoever's session made the API call, recoverable (if at all) only from application logs, not from a queryable column on the decision record itself.

## Part 7 — Decision Boundaries

Direct, evidence-only answers (no recommendation):

- **Should AI publish reports? Currently: no, and it does not** — `canPublishReport` is admin-tier gated; no AI call site was found this session calling a publish function directly.
- **Should AI promote learners? Currently: no, and it cannot** — Promotion has zero AI involvement anywhere in this audit series; both promotion tables are human-actor-only in their route gating (even though unreachable in practice).
- **Should teachers modify evidence? Currently: yes, but only through the four lifecycle functions** (`confirmReview`, `rejectReview`, `retractEvidence`, `eraseEvidence`) — direct row mutation is blocked by a DB trigger (CLAUDE.md-governed), so "modify" is structurally limited to state-machine transitions and superseding corrections, never an in-place edit.
- **Should parents modify assessments? Currently: no, and no code path was found that allows it** — restated 6E Part 8's exhaustive search found zero parent writes to `class_assessments`/`learner_evidence`, with the one flagged edge case (`app/api/parent/assessments/process`) being a deliberate teacherless-student self-service design, not a parent overriding a teacher's record.
- **Should students change learning records? Currently: no** — a student's own writes are confined to their own Compass session content, academy reflections/submissions, and career search triggers — none of which is a "learning record" in the Evidence/Projection sense; students cannot write to `learner_evidence` or `learner_projections` directly, only produce the raw activity that a separate pipeline may later turn into evidence.
- **Should AI decide a career recommendation autonomously? Currently: yes, and this is the one place this audit found AI operating past every boundary observed elsewhere** — restated Part 3, no human approval gate exists between generation and the student/parent seeing (and the system persisting) the result.

## Part 8 — Decision Conflicts

| Conflict pair | Where it occurs | Nature |
|---|---|---|
| **Teacher / Admin** | Assessment management — `canManageAssessment` genuinely permits both, intentionally (Sprint 6E Part 2 flagged this as the one *designed* overlap in the platform) | Intentional, not a defect — but since admin-tier is unreachable in production (Part 2), this "conflict" has, per this session's evidence, never actually been exercised by two different real actors |
| **Teacher / System** | Evidence auto-confirmation — a teacher's marking action and the system's confidence-based auto-confirm rule both effectively "decide" the same evidence row is trustworthy, at the same moment, by design | Intentional and layered (the teacher's act of entering data *is* the trust signal the system rule keys off), not a duplicate decision so much as one decision with two names |
| **Parent / Teacher** | **None found** — restated 6E Part 8's exhaustive search found no case where a parent and a teacher can independently make the same academic decision; parents are read/link-only by design |
| **AI / Human** | Career Intelligence (Part 3) — AI decides and executes with no human counterpart ever weighing in on the same specific decision (this is not a *conflict* in the sense of two actors disagreeing, but a **vacancy**: no human decision exists to conflict with, because none is ever made) | Structural absence of a human counterpart, not a live conflict |
| **AI / Human** | Adaptive Learning / Holiday Planner — here a genuine conflict-resolution mechanism exists: the AI proposes, the teacher's approved/adjusted version is what's stored and used, and the two are kept distinct (Part 5) | Resolved by design — the clearest example of a well-handled AI/Human decision boundary in the platform |
| **Legacy / Core** | Admission, Class Allocation, Promotion, Enrollment, Report Cards — restated extensively across 6A–6F: two independent pipelines exist for each, capable of reaching different conclusions about the same learner with no reconciliation | **Structural, unresolved** — the platform's largest category of decision conflict, though in practice muted by the fact that the Core side of each pair is almost always the unreachable one |
| **Ownership overlaps** | `teacher_id`-of-record vs. current-teach-relationship (CLAUDE.md's own explicitly-named risk) — a teacher who once entered evidence retains RLS-level access forever (Sprint 6E Part 8's `learner_evidence_own_teacher` finding), independent of whether they still teach the learner | A latent conflict between two different definitions of "whose decision is this" — attribution vs. current authority — flagged by CLAUDE.md itself as a rule precisely because this conflict is easy to introduce by accident |

## Part 10 — Decision Lifecycle

Tracing three major decisions from proposal through archive, per the sprint's request:

**Evidence confirmation** — Proposal: a claim is inserted (`pending_review` or straight to `auto_confirmed`, per confidence). Review: a teacher opens the Compass evidence review screen (or the system auto-confirm rule fires). Approval: `confirmReview`/`rejectReview`, DB-trigger-enforced transition. Execution: the row's `lifecycle_state` changes; nothing else happens synchronously. Publication: **implicit** — a confirmed row simply becomes visible to `findConfirmedEvidenceForLearner`, with no separate "publish" step (confirmation *is* publication for this decision). Audit: full (Part 9). Archive: **not found** — confirmed evidence persists indefinitely; no archival/retention policy was found this session (restated 6F Part 12's platform-wide "Archive is the most commonly missing lifecycle stage" finding). **This lifecycle does not stop prematurely** — it is the one decision in this audit that runs cleanly from proposal to a durable, traceable, if unarchived, end state.

**Report Card publication** — Proposal: `generateReportCards` computes and inserts draft rows (Core pipeline). Review: **no step found** — nothing in the code path between generation and publish resembles a review (no `pending`/`draft`-vs-`ready` distinction beyond the `is_published` boolean itself). Approval: `canPublishReport`, admin-tier only. Execution: `is_published = true`, `published_at` set. Publication: the same event as approval — no separate "make visible to parent" step distinct from the publish flag flip. Audit: partial (Part 9). Archive: not found. **This lifecycle stops prematurely at Review** — there is no code-modeled space for a headteacher (or anyone) to actually read and sign off on a report card's content before it is either published or not; the `headteacher_comment` column (Part 6) is schema evidence that this step was anticipated but never built into the actual generation/publish code path.

**Promotion** — Proposal: in theory, a teacher or admin calls the promote route with a target grade. Review: **no step found** — no reviewing party distinct from the proposer exists in either table's schema. Approval: implicit in the same API call (`processed_by` records who acted, not a separate approver). ## Part 12 — Educational Authority Assessment

**Determination, using only in-repository evidence: EduNexus currently reflects Teacher Authority as its dominant, almost exclusive, educational philosophy — with one narrow but consequential exception where AI Authority has been granted (Career Intelligence) without an equivalent human counterpart.**

- **Teacher authority**: every decision that actually executes in production today — Admission, Class Allocation, Assessment (create/mark/publish), Evidence confirmation — is made by the class teacher, restated across Parts 1, 2, 7. This is not a partial or shared model; it is close to total, by elimination (Administrative authority cannot be exercised, per Part 2's confirmation that the admin-tier roles are ungrantable).
- **Administrative authority**: exists fully in the permission/schema layer (`SCHOOL_ADMIN_ROLES`, `canPublishReport`, Withdrawal/Transfer/Promotion routes) but, per Sprint 6E and restated throughout this document, **cannot be exercised by any real actor in the current product** — this is Administrative Authority *designed for* but not *present*.
- **Shared authority**: found in exactly one place with real teeth — Assessment management's admin-tier-or-class-teacher gate (`canManageAssessment`) — but since the admin side is unreachable, this is Shared Authority *on paper* only.
- **AI-assisted authority**: the dominant, correct pattern for six of the seven AI-touching subsystems this audit found (Evidence extraction, Adaptive Learning, Holiday/Remedial Planning, Lesson Plan/SOW/Slides/Insha) — AI proposes, a teacher decides.
- **System authority**: limited to pure computation (ranking, term averaging) and rule-based automation with documented override windows (auto-confirm, holiday auto-publish fallback) — never a judgment call about a learner's education.
- **AI authority, unbounded**: **Career Intelligence is the one place this audit found AI Authority in the strict sense** — deciding and executing with no teacher or parent counterpart in the loop at all (Part 3, Part 7). This is the single point in the entire platform where the "Teacher Authority" philosophy that governs everything else does not apply.
- **Undefined authority**: found nowhere as a *distinct* category from the above — every decision this audit traced maps cleanly onto one of Teacher/Administrative(inert)/AI-assisted/System, except Career Intelligence, which is better described as AI authority than as undefined.

**This is not evaluated as a defect, per this document's own scope** — it is a description of what the current code implements, restated as this sprint's specific contribution: EduNexus is not a system with an *undefined* authority model, as one might assume from Sprint 6E's finding that the admin tier is inert. It has a **clear, if narrow and largely unintentional, authority model**: the teacher decides almost everything, AI proposes for the teacher to approve almost everywhere it touches learning, and administration exists as a fully-specified but entirely unexercised design.

## Part 13 — School Operating System Readiness

Using only repository evidence, and restating this series' four completed layers:

- **Organizational model** (Sprint 6E): present in schema/permission form, largely inert in practice — a real actor taxonomy exists but most of it cannot be populated.
- **Workflow model** (Sprint 6D): present for the teacher-driven paths, absent or unreachable for administrative paths — the best-designed workflow (End-of-Term) has zero UI callers.
- **Information model** (Sprint 6F): strong for the Evidence→Projection spine, fragmented/duplicated elsewhere, with a confirmed dead-end event bus.
- **Decision model** (this sprint): strong for exactly one decision (Evidence), traceable-but-thin for a handful more (Promotion/Transfer), and absent-to-nonexistent for the rest — the same bimodal pattern Sprint 6F found for information trust levels (Part 10 of that sprint) recurs here for decision authority.

**Determination**: the four layers, read together, tell a **consistent, not contradictory, story** — the same subsystem (Evidence/Projection) is simultaneously the best-organized (6E: correctly separated actor responsibilities for review vs. auto-confirm), best-flowing (6F: the one validated information chain), and best-decided (6G: the only fully traceable decision) part of the platform. The same subsystem (Core's institutional/administrative layer) is simultaneously the least populated actor set (6E), the most workflow-dormant (6D), the most duplicated/disconnected information source (6F), and the least exercised decision authority (6G). **EduNexus does not yet possess all four layers required for a School Operating System** — it possesses all four *in one vertical slice* (the Evidence/Projection/Intelligence spine) and close to none of them in the institutional/administrative slice that a real school's day-to-day operation (admission, promotion, graduation, reporting, discipline, attendance) would also require. A School Operating System needs both slices working; this audit series has now documented, with consistent evidence across four independent lenses, that only one currently does.

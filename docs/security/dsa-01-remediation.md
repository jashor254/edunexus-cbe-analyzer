# DSA-01 — shared reports behind a service-only token boundary

**Status (2026-11-04):** implemented, verified locally, PR open. **NOT applied to production, NOT deployed, NOT merged.**

> **Update — production-boundary stabilization (same day).** (1) `POST /api/share/generate` is now **disabled (HTTP 410)** behind a code-pinned kill switch (`lib/sharedReports/generationGate.ts`): auth still runs first (401 for anonymous callers), then the gate, before any body read or database work; no record can be created. (2) The public page is **origin-aware**: client-supplied content reads "Shared via EduNexus · not verified by EduNexus" and the report date is the creation date; only `server_generated` rows keep the EduNexus-authorship wording (the RPC now returns `provenance`; unknown values are treated as the least authoritative). (4) Supabase key names follow `docs/engineering/supabase-api-keys.md`. R13 (client-supplied content presented as EduNexus-generated) is **closed**.

## 1. The vulnerability and the boundary
`public.shared_reports` carried a PUBLIC `SELECT … USING (true)` policy, so any anonymous Data API caller could list every report — token, student name, grade, full payload. The deployed schema is expected to carry the same policy.

New boundary (one migration, `20261104120000_shared_reports_token_boundary.sql`):
- `anon` has **no** privileges on the table; `authenticated` keeps owner-scoped `SELECT` and `DELETE` only (no direct INSERT/UPDATE/TRUNCATE).
- Bearer-token reads go through `get_shared_report_by_token(text)` — `SECURITY DEFINER`, `search_path=''`, no dynamic SQL, EXECUTE **service_role only**, fixed DTO, exact-match lookup.
- Unknown / revoked / malformed / legacy-format tokens → zero rows (indistinguishable). Expired → status only, no personal data.
- Revocation: `revoked_at` + owner-only `POST /api/share/revoke` (opaque 404 for non-owners).

## 2. Token format and entropy (corrected)
Tokens are **32 base64url characters** from `crypto.randomBytes(24)` — **192 bits**, 6 bits per character (32 × 6 = 192). They are **not hexadecimal**: 32 *hex* characters would carry only 128 bits. An earlier draft of this document conflated the two; the generator never produced hex of that length.

Measured on 200,000 generated tokens: 200,000 unique; every token 32 chars; Shannon entropy **5.99999 bits/char**; worst per-position χ² 91.1 (df = 63; the 99.99th percentile is ≈103, so uniform); all 192 bits balanced; every token round-trips to exactly 24 bytes with canonical encoding. Enforced in CI by `lib/sharedReports/sharedReports.test.ts` (20,000-sample statistical test + a static check that only `randomBytes` is used).

**Legacy 12-character (48-bit) tokens are retired.** Strict `^[A-Za-z0-9_-]{32}$` is enforced in four places that must change together: `lib/sharedReports/token.ts`, the lookup function, the `shared_reports_token_format` CHECK (stops any writer, service role included, from minting a weak token), and the revoke route. The migration also revokes any pre-existing non-32-char row (none expected). Negative tests: unit, role-based SQL, and HTTP (legacy token cannot be stored; a legacy-format link is a 404).

## 3. Report-creation controls (`POST /api/share/generate`)
This route has **no first-party UI caller** (documented orphan in the Sprint 13 / Release Gate 1 audits), so its input is treated as untrusted.
| Control | Server enforcement | Database enforcement |
|---|---|---|
| Payload schema | Zod `.strict()` — six known fields, unknown keys rejected (400), levels 1–4, bounded strings/lists, snake_case subject keys | lookup DTO whitelists the same six keys |
| Max size | body ≤ 32 KiB checked before parsing (413) | `shared_reports_report_size`: report ≤ 16 KiB |
| Max expiry | fixed 30 days; client cannot choose | `shared_reports_expiry_cap`: ≤ 90 days after creation, even for service role |
| Ownership | session user from `auth.getUser()`; `students.user_id = user.id` else 403; client cannot send owner/token/expiry/provenance (400) | `user_id` NOT NULL FK; owner-only RLS read |
| Provenance | stamps `client_supplied` | `provenance` column, CHECK in (`client_supplied`,`server_generated`) |
Name and grade come from the `students` row, never the client. **Not solved:** content is still caller-supplied, not derived from stored learner evidence, and the public page footer says "generated by EduNexus". Recommendation: derive content server-side from evidence, or remove the orphan route (see R13).

## 4. HTTP security (verified on a production build over real HTTP)
Real response headers for a valid report: `Cache-Control: private, no-store, max-age=0, must-revalidate` · `CDN-Cache-Control: no-store` · `Vercel-CDN-Cache-Control: no-store` · `Referrer-Policy: no-referrer` · `X-Robots-Tag: noindex, nofollow, noarchive` · `X-Frame-Options: DENY` · `X-Content-Type-Options: nosniff`. Identical on 404, expired, the `_rsc` redirect hop, RSC payloads, prefetch requests, and `/api/share/*` responses. No `Age`, no `x-nextjs-cache: HIT`, no CORS header. Contrast: an ordinary page is served `s-maxage=31536000` with `x-nextjs-cache: HIT`, which the same assertions reject.
Also: `<meta name=robots noindex>` and `<meta name=referrer no-referrer>`; no canonical/OG URL carrying the token; `robots.txt` disallows `/shared/`; the admin link is a plain `<a>` (no Next prefetch); `<Analytics>` is wrapped by `RedactedAnalytics`, which rewrites `/shared/<token>` to `/shared/[token]` before any event is sent (unit-tested). The page `await`s `params` as Next 16 requires and is `force-dynamic`.
Headers are scoped to the two share paths; site-wide hardening remains DSA-09.

**WhatsApp migrations review:** both additive and idempotent (`ADD COLUMN IF NOT EXISTS`, nullable, partial indexes), no policy/grant/RLS change: `whatsapp_inbound_log.meta_message_id` + unique partial index (webhook dedup); `notification_log.delivery_status`, `delivery_status_at`, `provider_error_code` + partial index on `whatsapp_message_id`. Committed code on `main` uses all five columns (`notification.repository.ts`, `observationPipeline.ts`). **Finding: production has neither migration applied** (no columns, no indexes, no migration rows as of 2026-11-04) — deploying `main`'s WhatsApp code before applying them would make delivery-status writes fail. Separate from DSA-01; not applied here.

## 7. Release sequence
1. Merge the WhatsApp pin PR (CI fingerprint gate returns to green on `main`).
2. Retarget this PR to `main`; CI must be green (fingerprint `f2c4cc56…`).
3. Pre-deploy, read-only: re-count `shared_reports` rows (expect 0), confirm `20260610105350` and the July hardening migrations are present.
4. Apply `20261104120000` immediately before promoting the Vercel deployment (one transaction; the self-check aborts it if the boundary is missing). Old reader + new migration breaks share links; new reader + old DB breaks them too — they ship together.
5. Smoke test with a synthetic account: generate → open in a private window → revoke → open (404); anon Data API list returns empty/denied; check the response headers.
6. Add a Vercel Firewall rate-limit rule on `/shared/*`.
7. Observe 7 days (`Failed to look up shared report` in logs).
**Rollback:** documented in the migration header; it re-opens DSA-01, so prefer fix-forward. **Partial failure:** the migration is atomic; if the app deploy fails after it, share links 500 (availability gap only — no exposure).
